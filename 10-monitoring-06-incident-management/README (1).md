#№ Решение

# Постмортем: Инцидент GitHub от 21–22 октября 2018 года

## Краткое описание инцидента

21 октября 2018 года в 22:52 UTC произошёл сетевой сбой между дата-центрами GitHub, вызвавший рассогласование реплик баз данных и приведший к деградации сервиса на 24 часа и 11 минут. Пользователи наблюдали несогласованные данные: созданные Issues и комментарии отображались, но исчезали после перезагрузки страницы. Инцидент затронул только метаданные (Issues, Pull Requests, вебхуки и т.п.), хранящиеся в MySQL. Git-репозитории оставались полностью доступны и не пострадали.

## Предшествующие события

- GitHub использовал географически распределённую архитектуру с дата-центрами на восточном и западном побережьях США.
- Метаданные хранились в кластерах MySQL с автоматическим управлением топологией через Orchestrator.
- В 22:52 UTC проводились плановые работы по замене неисправного сетевого оборудования (100G оптика) в восточном дата-центре.

## Причина инцидента

Сетевой сбой продолжительностью **43 секунды** привёл к:
- Потере кворума в системе Orchestrator.
- Автоматическому переносу роли primary-ноды MySQL на западное побережье.
- Возникновению двух независимых наборов данных: несколько секунд новых записей на востоке и более 30 минут — на западе.
- Невозможности безопасного восстановления согласованного состояния без риска потери данных.

## Воздействие

- **Длительность**: 24 ч 11 мин (с 22:52 UTC 21.10 до 23:03 UTC 22.10).
- **Затронутые компоненты**: Issues, Pull Requests, комментарии, вебхуки, GitHub Pages.
- **Пользовательский опыт**: частичная недоступность, «пропадающие» комментарии, устаревшие данные.
- **Очередь**: более 5 млн вебхуков и 80 тыс. сборок GitHub Pages.
- **Репутационный ущерб**: снижение доверия из-за длительного времени восстановления и неточных оценок ETA.

## Обнаружение

Инцидент был обнаружен внутренними системами мониторинга в **22:54 UTC** по множеству алертов. К **23:02 UTC** инженеры первой линии подтвердили аномалию в топологии баз данных.

## Реакция

- **23:07 UTC**: заблокированы внутренние инструменты развёртывания.
- **23:11–23:13 UTC**: инцидент переведён в статус «красный».
- Принято решение **приоритизировать целостность данных над доступностью сервиса**.
- Приостановлена доставка вебхуков и сборка GitHub Pages.
- Начат процесс восстановления из резервных копий (создаваемых каждые 4 часа).
- Развернуты дополнительные read-реплики для ускорения синхронизации.
- Проведена ручная синхронизация и переключение топологии обратно на восточный дата-центр.

## Восстановление

- **11:12 UTC 22.10**: все primary-ноды MySQL восстановлены в восточном дата-центре.
- **16:24 UTC**: достигнута полная синхронизация read-реплик.
- **23:03 UTC**: обработана вся очередь вебхуков и Pages; статус сервиса переведён в «зелёный».

## Последующие действия

### Технические меры
1. **Ограничение Orchestrator**: запрет автоматического переноса primary-нод между регионами.
2. **Улучшение статус-страницы**: переход к компонентному отображению состояния сервисов.
3. **Активизация проекта active/active/active**: поддержка отказоустойчивости на уровне дата-центров без влияния на пользователей.
4. **Ускорение восстановления из бэкапов**: исследование альтернативных стратегий (например, delayed replicas).

### Организационные меры
1. **Внедрение chaos engineering**: регулярное тестирование сценариев отказов.
2. **Улучшение коммуникации**: более точные оценки времени восстановления, резервные каналы публикации статусов.
3. **Анализ потерянных записей**: ручная сверка бинарных логов за 43-секундное окно; уведомление затронутых пользователей при необходимости.

> **Примечание**: Ни один пользовательский Git-репозиторий не пострадал — инцидент затронул только метаданные, хранящиеся в MySQL.
